Lesson 08 · No networking experience needed

Network programming with sockets: addresses, TCP/UDP, and client-server communication

By the end of this lesson you will run two programs on the same host that exchange bytes over a socket, extend that to concurrent clients and message broadcast, and serve a minimal HTTP response to a browser. Each concept is defined precisely before use.

Core definitions: an IP address identifies a host; a port identifies a process on that host. 127.0.0.1 is loopback. A socket is an OS-managed endpoint for network communication, referenced by a descriptor/handle. TCP provides reliable ordered byte stream; UDP provides unordered datagrams. POSIX sockets are the Linux/macOS API; Winsock is the Windows API.

1. Networks, protocols, and bytes

Two processes exchange data either on the same host (via files, pipes, or loopback networking) or on distinct hosts connected by physical links and wireless media. In the latter case they require agreed procedures governing transmission.

A network is a set of hosts connected by transmission media. A protocol is a specification defining message format, sequencing, and error handling. Network transmission carries bytes (values 0–255); higher-level data must be serialized to bytes by the sender and reconstructed by the receiver.

Definition: byte and encoding
All network payloads are byte sequences. Text such as "hi" is encoded to bytes (typically UTF-8 / ASCII: h=104, i=105). “Sending a message” means transmitting its byte encoding; the receiver decodes those bytes back to the original representation.

2. IP addresses and ports

Delivery requires two levels of addressing:

  • IP address identifies a host on the network. 127.0.0.1 is the IPv4 loopback address: it always designates the local host and is standard for development and testing. 192.168.1.5 is an example of a host address on a local network.
  • Port identifies a process (more precisely, a socket binding) on that host. Since a host runs multiple networked processes, the port number selects the recipient. Web services conventionally use 80 or 8080.
  • Combined form: 127.0.0.1:8080 denotes the process bound to port 8080 on the local host.

For development, select ports in the range 1024–65535. Ports below 1024 are privileged and require elevated rights on most systems.

3. TCP vs UDP

TCP and UDP are the two primary transport protocols. The selection determines reliability, ordering, and connection semantics:

PropertyTCPUDP
ModelConnection-oriented. Endpoints establish a connection, then exchange a continuous stream.Connectionless. Each datagram is addressed and transmitted independently.
Reliability and orderReliable and ordered. TCP retransmits lost segments and delivers bytes in transmission order.Unreliable and unordered. Datagrams may be lost, duplicated, or reordered.
OverheadHigher (connection state, sequencing, acknowledgements).Minimal (no connection state).
Typical useChat, HTTP, file transfer — where completeness and order are required.Real-time games, voice, video — where latency matters more than loss of individual updates.
C++ operationsconnect / accept / send / recvsendto / recvfrom

This lesson begins with TCP because its ordered, reliable byte stream simplifies initial client-server implementations.

TCP framing requirement: TCP delivers a byte stream, not discrete messages. Transmission of “hello” followed by “world” may arrive as “helloworld” in one read or as “hel” + “loworld” across two reads. Application protocols therefore define message boundaries — in this lesson, a terminating newline \n marks the end of each message.

4. Sockets and OS descriptors

Application code does not access network hardware directly; it requests kernel-mediated communication through defined system interfaces.

Definition: operating system
Windows, macOS, and Linux. The OS owns network interfaces and enforces isolation. Programs obtain and operate on network resources exclusively through OS interfaces.
Definition: descriptor / handle
When the OS grants a resource (“open this file”, “create this socket”), it returns a small integer reference — a file descriptor on Linux/macOS, a handle (of type SOCKET) on Windows, e.g. 3 or 7. Subsequent operations pass this reference to identify the resource: “transmit these bytes on descriptor 7”. When finished, the program releases it with close (POSIX) or closesocket (Windows).
Definition: socket
A socket is an OS-managed endpoint for network communication, referenced by a descriptor/handle. Creation specifies the address family and type — e.g. IPv4 (AF_INET) with a reliable stream (SOCK_STREAM for TCP). The program then binds, connects, transmits with send, receives with recv, and releases the descriptor on completion.

Summary: to communicate over a network, a program requests a socket descriptor from the OS, then uses that descriptor to transmit and receive bytes.

5. Winsock and POSIX socket APIs

Linux/macOS and Windows expose the same socket semantics through distinct interfaces:

  • POSIX / Berkeley sockets (Linux, macOS): socket(), bind(), listen(), accept(), connect(), send(), recv(), close(). Declared in <sys/socket.h>.
  • Winsock (Windows): functionally equivalent, with three differences: initialization via WSAStartup() before any socket call, release via closesocket() instead of close(), and termination via WSACleanup().

This lesson presents the POSIX form first, then isolates the Windows-specific lines. Application logic — bind, listen, accept, transmit — is identical across platforms.

6. Project 1: echo server and client, explained line by line

Echo designates a server that returns each received payload to its sender. It verifies bidirectional transmission before introducing broadcast or protocol logic.

Execution requires two terminals: one hosts server (binds and accepts), the other hosts client (connects and transmits).

6a. The TCP server

A TCP server executes five operations in fixed order:

  1. socket() — request a TCP socket descriptor from the OS.
  2. bind() — associate the descriptor with a local port (here 8080) and interface.
  3. listen() — mark the descriptor as accepting inbound connections and set the pending-connection queue length.
  4. accept() — block until a client connects; return a new connected descriptor dedicated to that peer. The listening descriptor remains open for further connections.
  5. recv() / send() — receive bytes and transmit the response on the connected descriptor, then close() it.
// server.cpp — Linux/macOS: g++ -std=c++17 server.cpp -o server
// Windows: see section 6c for the required additions.
#include <sys/socket.h>  // socket(), bind(), listen(), accept(), recv(), send()
#include <netinet/in.h>  // sockaddr_in: structure holding IP address + port
#include <unistd.h>      // close()
#include <iostream>
#include <thread>        // per-connection concurrency
#include <cstring>        // string utilities

// Executed once per accepted connection, on a dedicated thread:
void handle(int clientSocket){
    // clientSocket is the connected descriptor for this peer.
    char buf[1024]; // receive buffer for up to 1023 payload bytes
    // recv blocks until bytes arrive, returning the count received.
    // Capacity is limited to sizeof(buf)-1 to reserve space for a terminator.
    ssize_t n = recv(clientSocket, buf, sizeof(buf)-1, 0);
    if(n > 0){
        buf[n] = 0; // append null terminator for output as a C string
        std::cout << "got: " << buf;
        std::string reply = std::string("echo: ") + buf; // construct response
        // Transmit the response on the same connected descriptor:
        send(clientSocket, reply.c_str(), reply.size(), 0);
    }
    close(clientSocket); // release the per-connection descriptor; listener remains open
}

int main(){
    // 1. Request a TCP descriptor. AF_INET = IPv4, SOCK_STREAM = TCP byte stream.
    int serverSocket = socket(AF_INET, SOCK_STREAM, 0);

    // Permit immediate rebinding after restart (avoids TIME_WAIT retention):
    int opt = 1;
    setsockopt(serverSocket, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    // 2. Bind to port 8080 on all local interfaces (INADDR_ANY):
    sockaddr_in addr{};             // address structure with three assigned fields:
    addr.sin_family = AF_INET;      // address family: IPv4
    addr.sin_port = htons(8080);     // port in network byte order (see below)
    addr.sin_addr.s_addr = INADDR_ANY; // accept connections on any local interface
    bind(serverSocket, (sockaddr*)&addr, sizeof(addr));

    // 3. Mark as passive with a pending-connection queue of 10.
    listen(serverSocket, 10);
    std::cout << "listening on 8080... run the client in another terminal\n";

    // 4+5. Accept loop: each accepted descriptor is serviced on a detached thread.
    while(true){
        int clientSocket = accept(serverSocket, nullptr, nullptr); // blocks until connection
        std::thread(handle, clientSocket).detach(); // service concurrently; resume accepting
    }
}
Definition: htons and byte order
Hosts may store multi-byte integers in different byte orders (endianness). Network protocols specify big-endian transmission order (“network byte order”). htons (“host to network, short”) converts a 16-bit port number from host order to network order. Apply htons() to every port assigned to a socket address structure.

6b. The TCP client

A TCP client performs three operations: socket → connect → send/recv.

// client.cpp — g++ -std=c++17 client.cpp -o client
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h> // inet_pton: parse dotted-decimal IP text to binary
#include <unistd.h>    // close()
#include <iostream>
#include <cstring>

int main(){
    // 1. Request a TCP descriptor:
    int s = socket(AF_INET, SOCK_STREAM, 0);

    // 2. Specify the target: 127.0.0.1 (loopback) port 8080:
    sockaddr_in a{};
    a.sin_family = AF_INET;
    a.sin_port = htons(8080);
    inet_pton(AF_INET, "127.0.0.1", &a.sin_addr); // textual address -> binary form

    // Establish the connection. Blocks until the server accepts or reports failure:
    connect(s, (sockaddr*)&a, sizeof(a));

    // 3. Exchange data:
    const char* m = "hello server\n"; // \n delimits the message per framing convention
    send(s, m, strlen(m), 0);         // transmit bytes (excluding null terminator)

    char b[1024];
    ssize_t n = recv(s, b, sizeof(b)-1, 0); // block awaiting the response
    if(n > 0){ b[n] = 0; std::cout << "server said: " << b; }
    close(s); // release the descriptor
}

Verification: terminal 1 → ./server, terminal 2 → ./client. Expected client output: server said: echo: hello server.

Connection diagnostics: (1) Confirm the server process is running. (2) Confirm identical port numbers on both sides. (3) Confirm firewall authorization — approve the OS prompt on Windows. (4) Confirm the address is exactly 127.0.0.1.

6c. Windows compatibility — differing lines only

Identical logic with platform-specific initialization and release. Prepend the following:

#ifdef _WIN32
  #include <winsock2.h>   // Windows socket declarations
  #include <ws2tcpip.h>   // inet_pton on Windows
  #pragma comment(lib, "ws2_32.lib") // link the Windows networking library
#endif

// at the start of main():
#ifdef _WIN32
  WSADATA w;                    // receives Winsock version details
  WSAStartup(MAKEWORD(2,2), &w); // initialize Winsock version 2.2
#endif
// ... remainder identical, except:
//   close(s) -> closesocket(s)
// at the end of main():
#ifdef _WIN32
  WSACleanup(); // release Winsock resources
#endif

#ifdef _WIN32 conditionally compiles the enclosed lines on Windows only. A single source file thus builds on both API families.

Resource discipline: encapsulate the descriptor in a class whose destructor invokes close / closesocket (RAII, Lesson 04). Deterministic release then holds on all paths, including exceptions.

7. Concurrent clients with threads

Concurrency in this server derives from a single statement:

std::thread(handle, clientSocket).detach();

Without it, the accept loop would block in per-connection I/O and delay subsequent connections. A thread (Lesson 07) assigns each accepted descriptor to an independent execution path running handle: the main loop returns immediately to accept while established connections proceed in parallel.

8. From echo to broadcast chat

Echo responds to one peer. A broadcast server retains all connected descriptors and forwards each received message to every other peer:

  1. Maintain shared state: std::vector<int> clients; with a std::mutex serializing concurrent modifications.
  2. On accept: acquire the mutex, append the new descriptor, release.
  3. On receipt of a delimited line: acquire the mutex, transmit to each descriptor except the sender, release.
  4. Implement the client with two threads: one blocking on getline (standard input → send), the other blocking on recv (socket → standard output). A single thread cannot block on both sources simultaneously.
  5. Preserve message framing: terminate each transmission with \n. On reception, accumulate bytes until \n is observed, then emit one complete message.
  6. Extension: treat each client's first line as its identifier and prefix outbound messages (e.g. [Ravi] hi!).

9. Minimal HTTP response for browser clients

HTTP is a text protocol layered over TCP. A fixed-format header followed by a body suffices for a browser to render a response. Request http://localhost:8080 after transmitting the following on the accepted descriptor:

std::string body = "<h1>Hi from C++!</h1>"; // response payload
std::string header =
  "HTTP/1.1 200 OK\r\n"              // status line: success
  "Content-Type: text/html\r\n"      // payload media type
  "Content-Length: " + std::to_string(body.size()) + "\r\n"
  "Connection: close\r\n"            // terminate TCP connection after response
  "\r\n";                            // empty line: end of header, start of body
std::string response = header + body;
send(clientSocket, response.c_str(), response.size(), 0);
// Then navigate to http://localhost:8080 in a browser.

Subsequent step: read index.html from storage with ifstream and transmit its contents as the body — a minimal static file server.

10. UDP datagrams

UDP is connectionless: no connection establishment or acceptance phase exists. Transmission specifies the destination per datagram:

// UDP sender — no connect, no accept:
int s = socket(AF_INET, SOCK_DGRAM, 0); // DGRAM = datagram (UDP); STREAM = TCP byte stream
sockaddr_in a{};
a.sin_family = AF_INET;
a.sin_port = htons(9000);
inet_pton(AF_INET, "127.0.0.1", &a.sin_addr);
// sendto transmits the buffer to the specified address:
sendto(s, "ping", 4, 0, (sockaddr*)&a, sizeof(a));
// The peer receives with recvfrom(), which additionally reports the sender address.

Select UDP when occasional loss is acceptable (e.g. periodic position updates) and latency is critical. Select TCP when completeness and order are required (chat, file transfer).

✅ Exercises

  1. Execute the echo server and client. Modify the payload. Apply \n framing and emit each received line separately.
  2. Chat v1: retain connected descriptors in vector<int> and broadcast each message to all peers. Validate with three concurrent clients.
  3. Chat v2: add identifiers with mutex protection. Remove the mutex experimentally and observe the resulting inconsistency.
  4. HTTP: serve the contents of index.html and render it in a browser via http://localhost:8080.
