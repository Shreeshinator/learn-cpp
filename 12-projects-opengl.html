Build a game: Pong / Breakout with SFML (OpenGL under the hood)

Goal: implement a windowed Pong game operating at 60 frames per second. This project covers game loop, input / update / draw, FPS, SFML, OpenGL, GLFW, VAO, VBO, shader, velocity, dt, and collision detection.

Overview: A game loop runs input-update-render at 60 Hz; SFML abstracts window/input/graphics built on OpenGL. Each iteration polls input state, advances simulation by delta-time, and renders the frame.

1. The game loop: input / update / draw at 60 Hz

  • Game loop — while (window is open) { input; update; draw; } executed continuously. It is structurally analogous to a REPL, but frame-driven rather than input-blocking.
  • Input — sampling current key state. Example: isKeyPressed(W) indicates whether W is held. Paddle displacement applies only while the corresponding key is active.
  • Update — advancing simulation state: ball += velocity * dt. Velocity = displacement vector per unit time. dt (delta-time) = elapsed seconds since the prior frame (e.g. 0.016s at 60 Hz). Scaling by dt yields frame-rate-independent motion.
  • Draw — clear framebuffer → issue draw calls → present (display()). FPS (frames per second) quantifies render rate; 60 FPS = one frame per 1/60s. setFramerateLimit(60) caps the loop to reduce CPU/GPU load.
  • Collision — geometric overlap test. intersects() evaluates rectangle intersection; velocity components are negated on contact to simulate reflection.
Per-frame sequence at 60 Hz:
  INPUT:   sample keys (W/S for left paddle, Up/Down for right)
  UPDATE:  paddles += speed*dt, ball += vel, evaluate wall/paddle contact
  DRAW:    clear(black) -> draw(left) draw(right) draw(ball) -> display()
Repeat until window closure.
Notes: input sampling performs no mutation. Update applies dt scaling so observed speed is consistent across hardware. Rendering always begins from a cleared buffer to prevent frame retention artifacts.

2. SFML vs OpenGL vs GLFW

  • SFML (Simple and Fast Multimedia Library) — high-level multimedia framework: RenderWindow, RectangleShape, CircleShape, Keyboard. Provides window management, input, 2D rendering, and audio. Internally issues OpenGL calls.
  • OpenGL — low-level graphics API for direct GPU programming: explicit buffer management and shader specification. Approximately 50 lines are required to display a single triangle. Maximum control at maximum verbosity. Production 3D engines build on OpenGL/DirectX/Vulkan.
  • GLFW + GLAD — intermediate configuration: GLFW provides window creation and input; GLAD loads OpenGL entry points. Triangle submission remains explicit.
  • Selection: SFML is appropriate for initial 2D projects (Pong demonstrates loop, input, and collision concepts transferable to any framework). Direct OpenGL is appropriate when custom 3D rendering or shader control is required.
Comparison: SFML provides integrated abstractions with reduced configuration. OpenGL provides explicit GPU control requiring manual setup. GLFW isolates window/input management while retaining explicit rendering.

3. Installing SFML

# Windows with MSYS2 UCRT64 (recommended, matches this course):
pacman -S mingw-w64-ucrt-x86_64-sfml
# Then compile with:
g++ -std=c++17 pong.cpp -o pong -lsfml-graphics -lsfml-window -lsfml-system

# Ubuntu / Debian / Mint:
sudo apt update
sudo apt install -y libsfml-dev
g++ -std=c++17 pong.cpp -o pong -lsfml-graphics -lsfml-window -lsfml-system

# Mac with Homebrew:
brew install sfml
g++ -std=c++17 pong.cpp -o pong -lsfml-graphics -lsfml-window -lsfml-system
# If Mac reports library not found, run: brew info sfml (displays required -I/-L flags)
Compiler invocation: pong.cpp = translation unit. -o pong = output executable. -lsfml-graphics -lsfml-window -lsfml-system = link three SFML components: graphics (2D primitives), window (context + input), system (clock/time). Each must be specified; omission yields undefined reference link errors. On Windows, execute installation and compilation within the MSYS2 UCRT64 environment so PATH resolves SFML.

4. Complete Pong implementation

// pong.cpp -- g++ -std=c++17 pong.cpp -o pong -lsfml-graphics -lsfml-window -lsfml-system
#include <SFML/Graphics.hpp>
#include <algorithm>
int main() {
    sf::RenderWindow win(sf::VideoMode(800, 600), "Pong - C++");
    win.setFramerateLimit(60);
    sf::RectangleShape left(sf::Vector2f(15, 100));
    left.setPosition(20, 250);
    sf::RectangleShape right(sf::Vector2f(15, 100));
    right.setPosition(765, 250);
    sf::CircleShape ball(10);
    ball.setPosition(390, 290);
    sf::Vector2f vel(4.f, 3.f);
    float leftY = 250, rightY = 250;
    sf::Clock clock;
    while (win.isOpen()) {
        sf::Event e;
        while (win.pollEvent(e)) {
            if (e.type == sf::Event::Closed) win.close();
        }
        float dt = clock.restart().asSeconds();
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::W)) leftY -= 400 * dt;
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::S)) leftY += 400 * dt;
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Up)) rightY -= 400 * dt;
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Down)) rightY += 400 * dt;
        leftY = std::max(0.f, std::min(500.f, leftY));
        rightY = std::max(0.f, std::min(500.f, rightY));
        left.setPosition(20, leftY);
        right.setPosition(765, rightY);
        ball.move(vel);
        auto p = ball.getPosition();
        if (p.y < 0 || p.y > 580) vel.y = -vel.y;
        if (ball.getGlobalBounds().intersects(left.getGlobalBounds()) ||
            ball.getGlobalBounds().intersects(right.getGlobalBounds())) {
            vel.x = -vel.x * 1.05f;
        }
        if (p.x < -20 || p.x > 800) {
            ball.setPosition(390, 290);
            vel = {4.f, 3.f};
        }
        win.clear(sf::Color::Black);
        win.draw(left);
        win.draw(right);
        win.draw(ball);
        win.display();
    }
    return 0;
}

5. Pong walkthrough

Part A — window initialization:
#include <SFML/Graphics.hpp> — SFML graphics module (window, shapes, color).
#include <algorithm> — standard algorithms including std::max/min.
sf::RenderWindow win(sf::VideoMode(800,600), "Pong - C++"); — creates an 800×600 render window. sf:: is the SFML namespace. VideoMode specifies dimensions. Coordinate origin is top-left (0,0); x increases rightward, y increases downward.
win.setFramerateLimit(60); — limits the loop to 60 iterations per second.
Part B — scene objects:
sf::RectangleShape left(sf::Vector2f(15,100)); — 15×100 rectangle. Vector2f = two-component float vector.
left.setPosition(20,250); — positions top-left corner at (20,250) (vertically centered: 600/2 − 50 = 250). Right paddle x=765 (800 − 20 − 15).
sf::CircleShape ball(10); — circle radius 10 (20px diameter). ball.setPosition(390,290); — approximately centered (800/2−10, 600/2−10).
sf::Vector2f vel(4.f, 3.f); — velocity per-frame displacement: +4 x (right), +3 y (down). Negative components reverse direction.
float leftY=250, rightY=250; — tracked paddle y-coordinates; x remains fixed.
sf::Clock clock; — elapsed-time source. restart() returns interval since prior call and restarts measurement.
Part C — input and delta-time:
while (win.isOpen()) — game loop; terminates on window closure.
while (win.pollEvent(e)) if (e.type==Closed) win.close(); — drains the OS event queue (close requests, etc.). pollEvent returns pending events. Required on Windows to maintain responsiveness.
float dt = clock.restart().asSeconds(); — seconds elapsed since prior frame (nominally 0.016). Enables hardware-independent speed.
Four isKeyPressed branches: W/S control left paddle, Up/Down control right paddle. Displacement 400*dt = 400 px/sec × seconds (~6.6px at 60 Hz). Negative y = upward (coordinate system).
leftY = max(0, min(500, leftY)); — clamps position to [0,500] (500 = 600 − 100 paddle height).
setPosition applies the computed coordinates.
Part D — ball integration, collision, reset:
ball.move(vel); — translates ball by velocity (calibrated for the 60 Hz limit).
auto p = ball.getPosition(); — retrieves top-left position. auto = deduced type.
if (p.y<0 || p.y>580) vel.y=-vel.y; — vertical wall contact (580 = 600 − 20 ball diameter); negates y-component (reflection).
if (ball.getGlobalBounds().intersects(...)) — getGlobalBounds() returns the axis-aligned bounding box. intersects tests rectangle overlap. On paddle contact, negates x-component and scales by 1.05f (5% acceleration).
if (p.x<-20 || p.x>800) — lateral exit indicates a scored point. Resets ball to center and restores initial velocity.
win.clear(Black); win.draw(...); win.display(); — clears to black, submits each drawable, then display() presents the completed frame. Omitting display leaves the window unpresented.

6. VAO / VBO / shaders

Technical summary: The GPU processes triangles. A VBO (Vertex Buffer Object) stores vertex attribute data (positions, colors) in GPU memory. A VAO (Vertex Array Object) records the attribute binding configuration for VBOs. A shader is a GPU-executed program: the vertex shader transforms vertices to clip space; the fragment shader computes per-pixel color (written in GLSL). Per frame, SFML binds the appropriate VAO, activates shaders, and issues glDrawArrays(GL_TRIANGLES,...) for each drawable. SFML encapsulates this pipeline; direct OpenGL development requires explicit management of each stage.

7. Breakout extension

  1. Mouse-controlled paddle: per frame, auto m = sf::Mouse::getPosition(win); paddle.setPosition(m.x - 50, 550); (−50 centers a 100px paddle on the cursor). Clamp x to [0,700].
  2. Brick grid: std::vector<sf::RectangleShape> bricks; populated as 3 rows × 8 columns (90×25 cells, 10px spacing), distinct setFillColor per row. Render via iteration.
  3. Ball-brick collision: iterate bricks; on ball.getGlobalBounds().intersects(bricks[i].getGlobalBounds()), negate vel.y, erase the element (bricks.erase(bricks.begin()+i);), increment score, break (single removal per frame).
  4. Lives and termination state: int lives = 3; Ball below y=600 → decrement, reset ball. If lives==0 or bricks.empty(), display sf::Text (“You win!” / “Game over”). sf::Text requires a loaded font: sf::Font f; f.loadFromFile("arial.ttf"); text.setFont(f); (place a .ttf adjacent to the executable).
  5. Collision audio: integrate Lesson 11 miniaudio: invoke ma_sound_start(&blip); within the collision branch.
Recommended order: mouse input validates event handling. Brick storage validates containers and iteration. Collision validates index-safe removal. Lives/text validate state transitions. Audio validates cross-lesson integration. Implement and test each stage independently.

✅ Exercises

  1. Score display: maintain int scoreL=0, scoreR=0; Left exit → scoreR++; right exit → scoreL++. Render via sf::Text. First to 5 triggers victory display and halts ball motion.
  2. Breakout implementation: follow section 7 sequentially. Begin with paddle plus one brick row, expand to three rows, then add lives logic.
  3. Collision audio: play blip.wav (Lesson 11) on paddle/wall contact using miniaudio. Validate audio and graphics linkage independently before merging.
  4. Velocity limit: the paddle reflection applies *1.05f acceleration. Impose a maximum (e.g. inhibit boost when abs(vel.x)>12) to preserve playability.
